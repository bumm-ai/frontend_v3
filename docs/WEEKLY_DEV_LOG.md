# Тижневі dev-звіти — правило «продовження»

**Повна історія проєкту (4 частини, від старту до поточного стану):**  
[Week 1](./DEV_LOG_BUMM_WEEK_01.md) → [Week 2](./DEV_LOG_BUMM_WEEK_02.md) → [Week 3](./DEV_LOG_BUMM_WEEK_03.md) → [Week 4 — зараз](./DEV_LOG_BUMM_WEEK_04.md)

Кожен новий звіт — **не копія повного опису продукту**, а **логічний наступний крок** після попереднього періоду. Так видно прогрес для хакатону / менторів / інвесторів.

---

## Як писати (обов’язкова структура)

1. **Зв’язок із попереднім звітом** (2–4 речення)  
   - Що вже було зафіксовано раніше (коротко: «після звіту за …» або «на базі минулого тижня»).

2. **Що зроблено саме за ЦЕЙ тиждень** (дельта)  
   - Нові ендпоінти, хуки, екрани, рефактори, багфікси — конкретно.  
   - Якщо «тиждень» = полірування — так і назви: стабілізація, тести, UX.

3. **Як це продовжує попередню віху**  
   - Одним абзацом: чому це наступний крок (наприклад: «після step-mode додали реальний час, щоб не чекати всліпу»).

4. **Знімок стану (опційно)**  
   - Лише якщо змінилась архітектура; інакше не повторюй увесь стек щотижня.

5. **Фокус на наступний період** (1–3 пункти) — опційно.

---

## Анти-патерн

- Повторювати щотижня той самий довгий список «у нас є LangGraph, REST, WS…» без нових акцентів.  
- Писати звіт лише як «огляд репозиторію» без прив’язки до **часу**.

---

## English (same rule)

Each weekly report is a **sequel**, not a full product re-spec.

**Required:** (1) Link to the previous report. (2) **Delta** — what landed *this* week. (3) One paragraph on **why this is the logical next step**. Optional: snapshot, next focus.

**Avoid:** Pasting the same full stack description every week.

---

## Приклад: тиждень як продовження базового періоду

**Контекст (попередній звіт / база):** Зафіксовано step-mode пайплайн, тонкий фронт, `deriveUIFromStatus` + `pendingStep`, WS статусу контракту, чат і модалки кроків, юніт-тести на кнопковий стан.

**Цей тиждень (продовження):** На цій базі доведено **шар реального часу** і **прозорість змін коду**: SSE-стрім логів білду в UI, WebSocket кредитів через Redis + `wsHub` / `balanceBus`, ендпоінт історії коду та перегляд diff фіксів у `AuditModal`, хук `useContractStream` для єдиного стріму статусу без дублювання клієнтських прапорців генерації. Це логічний розвиток: спочатку коректний стан кнопок і кроків, потім — видимість логів, балансу та «що саме змінив фікс».

**Дати:** підстав вручну `[тиждень після базового звіту]`.
